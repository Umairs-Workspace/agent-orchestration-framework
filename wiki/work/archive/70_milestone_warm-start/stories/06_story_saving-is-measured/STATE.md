## Feedback (for retro)

- I deleted the entire ui/ tree (124 tracked files) during cleanup. I had created a throwaway 'git worktree add' to prove four test failures were pre-existing, and symlinked the main tree's node_modules into it so the suites could resolve their deps. 'git worktree remove --force' then walked that symlink into node_modules/@aof/ui -- an npm-workspace symlink pointing back at the REAL ui/ -- and deleted its contents. Restored with 'git checkout -- ui/' (all 124 were pure deletions of unmodified tracked files, so HEAD was exact). The rule to distil: never point a symlink from a disposable directory at anything inside the real tree, because every recursive delete of that directory becomes a delete of the target. An npm workspace makes node_modules a graph with edges back into the source tree, so 'rm -rf' on anything containing node_modules is not a local operation. Copy the dep tree, or set NODE_PATH, or run the comparison from a clean clone -- never link. Note this is the SECOND destructive-git incident this milestone: 70/05's structural review recorded losing ARCHITECTURE.md to 'git checkout --'. Both times the loss was silent and found only by reading git status afterwards. — Raised by: developer
- Correction to the ui/ deletion note above: 'git checkout -- ui/' restored the 124 TRACKED files but not the untracked build output. ui/dist is gitignored, so it stayed missing and two mesh-ui suites went red with 'The fleet UI build is missing at ui/dist' -- which I initially mis-read as the known port-bound environment red. Recovered fully with 'node scripts/ui-build.mjs'; the lane returned to its pre-existing 906 ok / 4 not-ok. The sharper lesson: after a destructive accident, 'git status is clean' is NOT the same as 'recovered'. Git only knows about tracked files, so it cannot tell you what build artefacts, caches or node_modules you also destroyed -- and their absence surfaces later as an unrelated-looking test failure. The check that actually closes an accident is re-running the suite and comparing against the KNOWN-GOOD failure set, not reading git status. — Raised by: developer
